## Blocking finding

### Finding 1 — Clipboard-history/clipboard-manager software is an unclassified channel, structurally closer to Class D's silently-fatal reasoning than to Class A's one-shot residual

**What the ADR does today.** Class A treats copy/paste as an irreducible, owner-elevated, one-shot transcription: "A person who can read a value can transcribe it... The project claims no control here and must not imply otherwise." Class D separately singles out *background* software that silently converts the residency's existence into a durable copy or description outside it — backup and content indexing are named "silently fatal" precisely because they happen without any further owner action, purely because the residency exists on disk. Class D also explicitly names the parallel background-software case for screen capture ("third-party screen-capture or screen-recording software holding the relevant system permission") as distinct from owner-initiated Class A screenshots.

**The gap.** A clipboard-history manager (e.g., a menu-bar clipboard manager, or an OS-level clipboard history feature) is common consumer/developer software that silently persists *every* copy event to a local database — and, in several shipping products, syncs that database to other devices or the cloud — the instant the owner performs any Class A copy, with no further owner action and often without the owner's contemporaneous awareness that history is being retained. This is not the same shape as Class A's "a person who can read a value can transcribe it": Class A assumes a deliberate, bounded, single act by the owner (the owner types out or pastes the value somewhere once, on purpose); a clipboard-history manager instead converts *any* copy — including a copy the owner intends to immediately paste back inside the same viewing session, with no external destination in mind at all — into an automatically retained record outside the residency, exactly the same failure shape ADR-0031 Decision 7 uses to make backup/indexing `NEVER_CROSSES` by description. It is neither named as a fifth class nor folded explicitly into Class D's enumerated list ("Backup... content indexing... synchronization software... screen-capture or screen-recording software"), so under the ADR's own default rule ("a channel that is unrecognized... is treated as boundary-relevant and blocks the session") a preflight built strictly from the current enumeration would not check for it, and the attestation's condition 3 ("the owner performed no Class A elevation whose result left quarantine... no paste into a document outside the residency") does not by its own text cover the case where the *copy itself*, not a subsequent paste, is what leaves the residency.

**Why this is in scope and not a hypothetical.** Measurement 2 explicitly asks to probe for a channel the classification misses and to check whether something the vehicle *could* control, or observe and refuse on, has instead been filed under an irreducible residual it doesn't actually match. Clipboard-history software is exactly as observable in principle as the screen-recording-permission case Class D already handles (both are backgrounded, permissioned, or enumerable OS-level facts about the workstation) and exactly as silently consequential as content indexing — yet it received neither the "workstation precondition, checked by preflight" treatment nor an explicit residual naming, while its two closest structural cousins (indexing/backup, and screen-recording) both did.

**Recommended repair shape (not prescribed, Reviewer's choice is not binding):** add clipboard-history/clipboard-manager retention to Class D's enumerated preconditions (observed and refused where mechanically detectable, e.g., known clipboard-manager processes or the OS's own clipboard-history feature if present, and named as an owner-knowledge residual analogous to condition 4 where it is not), and narrow or footnote Class A/condition 3 so a bare copy-with-no-external-paste is not silently assumed innocent when such software may be running.

## Non-blocking observations

### Observation 1 — The platform-impossibility claim underlying Class C is broader than the evidence needs it to be

Both the ADR ("On macOS there is no per-process network boundary available without root or a third-party control") and its analysis ("On macOS there is no way to give one process its own network boundary without administrator control") state, as settled fact, that per-process network confinement is unavailable on macOS without root or third-party software. macOS's built-in Seatbelt sandbox tooling (`sandbox-exec` and the underlying sandbox profile mechanism Chrome itself uses for its own renderer-process sandbox) can, in principle, deny same-UID, non-root network access to an arbitrary child process without installing any third-party software — it is part of the base OS, not a third-party control, and does not require administrator privileges to invoke against a process the invoking user owns. This does not change the milestone's decision (ADR-0044 already routes *any* substrate selection, evaluated or not, to a separate future implementation milestone, and this ADR selects none), and it does not weaken the Guarded Transport analogy, which is the actual basis for rejecting the vehicle-first shape. But the categorical phrasing overstates what has actually been ruled out: no evaluation of `sandbox-exec` (or Chrome's own existing internal sandbox machinery) as a same-UID mitigation is recorded anywhere in the corpus, so stating its absence as an established platform fact — rather than "not yet evaluated" — could mislead a later foreman into treating a real, unevaluated candidate as already foreclosed. Recommend softening to something like "no per-process network boundary is currently selected or verified for this project" rather than asserting platform impossibility, should this text be touched during the Finding 1 repair.
