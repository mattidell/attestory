## Findings

### RKE-R1 (low — test-evidence gap): `ClosureWalkMemo` random graphs do not fail when cycle-disjointness guards are removed

- **Location:** `tests/test_track1_memos.py:242-287`, `packages/derivation/presentation_projection.py:580-597`
- **Violated claim / question:** Charter Question 4 ("Do the new tests fail when their memo is wrong (stale hit, missed key field, changed walk)?").
- **Concrete failure scenario and reproduction:** In `packages/derivation/presentation_projection.py:584-595`, `memoized` guards reuse on `seen.isdisjoint(known.examined)` (line 584), absorbs `known` into `frames[-1]` on hit (line 585), and guards caching on `if result and frame.hits.isdisjoint(seen):` (line 594). Because `_closure_question_reasons` is a pure conjunction (`all(...)`) where any `False` child immediately aborts the entire top-level walk, mutating `presentation_projection.py` in memory to drop `frame.hits.isdisjoint(seen)`, drop `seen.isdisjoint(known.examined)`, or replace `frames[-1].absorb(known)` with `pass` produces **0 failures** across all 1,500 random graphs in `ClosureWalkMemo.test_matches_the_unmemoized_walk_on_random_graphs`. A concrete graph where dropping `frame.hits.isdisjoint(seen)` *does* return a wrong answer requires a synthesized family-validation row `C` (`artifact_id: "demo.famA.member-validation.synthesized"`, `missing: ["demo.K", "demo.fam0"]`, with `later_any_arm_refs=True`) reached first via `demo.P -> demo.K -> C` (where `"demo.K"` is in `seen`, so `if key in seen:` skips `explain(C, "demo.K")` and `C` returns `True` via `"demo.fam0"`) and second via `demo.Q -> C` (where `"demo.K"` is not in `seen`, so `explain(C, "demo.K")` adds `"famA meaning of K"` to `extras`). On that graph, both the committed implementation and `_reference_reasons` return `[{'sentence': 'Q0'}, {'sentence': 'famA meaning of K'}]`, whereas removing `frame.hits.isdisjoint(seen)` returns `[{'sentence': 'Q0'}]`. `_graph(rng)` in `tests/test_track1_memos.py:242-266` never hits that combination in 1,500 draws.
- **Consequence:** Evidence-only gap. The production walk memo in `packages/derivation/presentation_projection.py:576-597` is mathematically sound.
- **Smallest repair:** Add one deterministic unit test to `ClosureWalkMemo` in `tests/test_track1_memos.py` exercising the two-path synthesized-meaning cycle above so dropping `frame.hits.isdisjoint(seen)` fails the test.

### RKE-R2 (low — defensive memo boundary and test coverage): `_validation_memo_key` omits `corpus`, and `marshal.py` precompute has no dedicated unit test in `test_track1_memos.py`

- **Location:** `packages/derivation/production_resolver.py:119-157`, `packages/derivation/marshal.py:705-723`, `tests/test_track1_memos.py:66-121`
- **Violated claim / question:** Charter Questions 2 and 4 (stale entry under direct/monkeypatched calls; focused test coverage per fix).
- **Concrete failure scenario and reproduction:**
  1. `_validate_once(package, corpus, schemas, citizen_checksums)` (`packages/derivation/production_resolver.py:138-157`) takes `corpus` as an argument, but `_validation_memo_key(package, citizen_checksums, schemas)` (`production_resolver.py:119-135`) hashes only `(validate_package.__code__, package_digest, members, schema_digest)` and never inspects `corpus`. Along the production path (`resolve_production_package`, lines 497–501), `_resolve_member_corpus` runs immediately before `_validate_once` and admits each member into `corpus` only if `citizen_checksum(body) == citizen_checksums[(id, version)]`, so `citizen_checksums` uniquely pins `corpus`. However, if `_validate_once` is called directly with two different `corpus` dictionaries under the same `citizen_checksums` (as in `tests/test_track1_memos.py:69`, which passes `corpus={}`), or if a test monkeypatches `_resolve_member_corpus` (or an internal helper in `package_validation` other than `validate_package`) without changing `citizen_checksums`, the second call hits a stale cached verdict.
  2. `tests/test_track1_memos.py` tests the validation memo and the closure-walk memo, and `tests/test_track1_validation_index.py` tests the source-family index, while the fourth fix (`packages/derivation/marshal.py:705-723`, `required_by_any_rule`) relies on existing marshal/live tests rather than a dedicated unit test in `test_track1_memos.py`.
- **Consequence:** Non-blocking defensive/test note; no production caller can reach `_validate_once` with a `corpus` that disagrees with `citizen_checksums`.
- **Smallest repair:** Include a tuple of `(key, id_or_checksum)` from `corpus` in `_validation_memo_key` (or assert/document on `_validate_once` that `corpus` is checksum-verified against `citizen_checksums`), and optionally add a small synthetic test for `marshal_run_context`'s fallback union.

## Answers to Charter Questions

### 1. Identity

- **Does the evidence prove byte-identity across all 775 recorded lists?** Yes. `track1-summary-baseline.json` (regenerated from a pristine `git archive` export of `0763f572`) and `track1-summary-after.json` both record 775 lists (691 `success`, 84 `error` across `FindingModelError`, `HorizonModelError`, and `SourceAuthorityError`, 0 `refused`) with the identical aggregate `per_list_digest` (`3def5f6f845f2c0bee7500a17f6cdda0f0577a84de0331144b10a26f5356cab1`).
- **What `track1_dump.py` hashes and whether anything filer-visible could differ yet hash the same:**
  - For every `success` list, `track1_dump.py:77-87` records three distinct SHA-256 digests:
    1. `result_sha`: canonical JSON (`sort_keys=True`) of `{"report": report, "values": values}`, where `report` is the parsed `out.json` run report (all 315–319 disposition rows, authorization, etc.) and `values` is the sorted list of canonicalized derived publication findings.
    2. `page_sha`: SHA-256 of the raw UTF-8 HTML page bytes returned by `_render_page(REPO, capability, outcome.presentation_path)` (without JSON re-serialization or key sorting), with only the ephemeral temporary workspace directory path masked to `<TMP>`.
    3. `presentation_sha`: SHA-256 of the raw bytes of `outcome.presentation_path` on disk (with `tmp` masked to `<TMP>`).
  - For every `error` list (`track1_dump.py:88-93`), it records the exact exception class name (`type(exc).__name__`), the exact message string (`str(exc)` with `tmp` masked to `<TMP>`), and `result_sha`.
  - `per_list_digest` (`track1_dump.py:186-192`) hashes the tab-separated lines `<key>\t<outcome>\t<result_sha>\t<page_sha>\t<presentation_sha>\t<error>\t<message>` sorted by list key. Because both `page_sha` and `presentation_sha` hash raw file/page bytes directly (not key-sorted projections), nothing a filer sees on the page or in the presentation artifact could differ (even in key or element ordering) while hashing the same.
- **Independent sample verification:** We exported a fresh pristine copy of commit `0763f572` via `git archive` into a temporary directory outside the repository and ran `track1_dump.py`'s `per_list` and `validation_errors()` under `PYTHONHASHSEED=0` against both `0763f572` and `HEAD` on a four-list sample (`v81/case/m_8949_no_ic3_yes_q3_no` [median], `v83/track0/s0/b4_amount_no_answer` [success], `v81/case/a_corrected_basis_missing` [error], `v81/case/a_high_and_w_row` [error]) plus all five validation cases. All four sample lists and all five validation cases matched byte-for-byte (`result_sha`, `page_sha`, `presentation_sha`, `error`, `message`, `issues_digest`, `output_owners_sha`, `resolved_members_sha`).

### 2. Memo safety

- **Package-validation memo (`packages/derivation/production_resolver.py:110-157, 501`):**
  - *Key:* `(validate_package.__code__, package_digest, members, schema_digest)` where `package_digest` is the SHA-256 of canonical `package` JSON, `members` is `tuple((pin["id"], pin["version"], citizen_checksums.get((pin["id"], pin["version"]))) for pin in package.get("members", []))`, and `schema_digest` is the SHA-256 of all `(sid, schemas.get(sid))` documents in `schemas.schema_ids()`.
  - *Input changes / changed member bytes:* In `resolve_production_package` (lines 497–501), `_resolve_member_corpus` runs on every call before `_validate_once`, reading all candidate member files from disk and admitting a member body only if `citizen_checksum(body) == citizen_checksums[(id, version)]`. A modified member file on disk whose checksum does not match the registry is refused with `MEMBER_ABSENT_OR_MISMATCH` before `_validate_once` is called; a modified member accompanied by an updated registry checksum changes `members` in `_validation_memo_key` and misses the cache. See `RKE-R2` for the narrow direct-caller / monkeypatch caveat (`corpus` is not hashed independently of `citizen_checksums`, and monkeypatching a helper inside `package_validation` other than `validate_package` does not change `validate_package.__code__`).
  - *Lifetime and size bound:* Process-global `OrderedDict` bounded by `_VALIDATION_MEMO_LIMIT = 4` (LRU eviction via `move_to_end` and `popitem(last=False)`), with `clear_validation_memo()` provided.
  - *Mutable sharing:* Both `_VALIDATION_MEMO[key] = copy.deepcopy(validation)` on store (line 154) and `return copy.deepcopy(cached)` on hit (line 152) deep-copy the `PackageValidation` instance, so callers never share mutable `output_owners` or `resolved_members` dicts/lists.
- **Source-family index (`packages/derivation/package_validation.py:3046-3066, 3293-3304`):**
  - *Lifetime and size bound:* Local dicts (`bundle_fact_type_ids`, `closure_ids_by_fact_type`, `closure_v4_ids_by_fact_type`) constructed once per `validate_package` call over `resolved` (~1,053 members) immediately before the reachability loop and garbage-collected when `validate_package` returns.
  - *Staleness and mutation:* `resolved` is not mutated during the reachability loop; no state survives the call or is returned to callers.
- **Closure-walk memo and member index (`packages/derivation/presentation_projection.py:535-680, 700-724`):**
  - *Lifetime and size bound:* `members_by_id`, `owned_meanings`, and `memo` are local to a single `_closure_question_reasons` call, bounded by the number of resolved package members (~1,053) and blocked rows in `by_symbol` (~319). Nothing outlives the call.
  - *Object-id keys and staleness:* `owned_meanings` is keyed by `id(member)` for elements of `resolved_members`, and `memo` is keyed by `(name, id(current))` for row dicts in `by_symbol`. Because `resolved_members` and `by_symbol` remain alive for the entire `_closure_question_reasons` call, Python cannot recycle those object IDs during the call.
  - *Walk equivalence:* A walk frame is stored only when `result` is `True` and `frame.hits.isdisjoint(seen)` (implying `frame.examined.isdisjoint(seen)`, so the walk skipped nothing due to the incoming `seen`), and reused only when the new `seen.isdisjoint(known.examined)`. No cached `_WalkFrame` is returned to external callers; its sets are copied into `reasons` as sorted `{"sentence": sentence}` dicts.
- **Marshal precompute (`packages/derivation/marshal.py:705-723`):**
  - *Lifetime and size bound:* `required_by_any_rule: set[str] | None` is a local variable inside `marshal_run_context`, computed at most once per call on the first fallback finding and discarded on return. `rules` is not mutated during the loop.

### 3. Validation order

- **Is "same multiset always, same order under a fixed seed" true of the pristine and changed code?** Yes. In `packages/derivation/package_validation.py`, the Track 1 source-family index only populates `adj[m_id]` (a `set[str]`) for `source-family.v1` and `source-family.v2`. Furthermore, `bundle_fact_type_ids` is queried in the same `for p_id in member_ids:` order and `closure_ids_by_fact_type` / `closure_v4_ids_by_fact_type` preserve the exact `for _p2, c2 in resolved:` insertion order (deduplicated per citizen via `dict.fromkeys`), so `adj[m_id].add(...)` is invoked in the identical sequence. Under any fixed `PYTHONHASHSEED`, string hashes and set table layouts in `validate_package` are identical between pristine (`0763f572`) and changed (`HEAD`) code, producing the exact same ordered `issues` tuple (verified for seeds 0, 1, and 2 in `track1-validation-seeds.json` and our independent sample run). Across seeds, `adj` only feeds the BFS reachability set `visited` (lines 3396–3403), which is order-invariant, and the seed variation in `MEMBER_UNREACHABLE` ordering comes from `for m_id in member_ids:` at line 3405 iterating the unsorted `member_ids` set in both pristine and changed code.
- **Does any consumer depend on order?** No production or test consumer depends on the order of `MEMBER_UNREACHABLE` issues across hash seeds:
  - `packages/derivation/production_resolver.py:502-509` gates on `if not validation.ok:` and packs `validation.issues` into `Refusal("HARD_GATE_REFUSED", ...)`.
  - `packages/derivation/live.py:664-665`, `packages/tax/ssa_family_handover.py:111-114`, and `packages/tax/f1099k_statement_recording.py:189-192` check `isinstance(resolved, Refusal)` and read `resolved.reason` / `resolved.detail`.
  - `packages/derivation/runners/derive.py:81-92` ignores `validation.issues` and reads `validation.resolved_members`.
  - Tests in `tests/` compare `{issue.code for issue in result.issues}` (sets) or sorted multisets (`tests/test_track1_validation_index.py:77`).

### 4. Tests

- **Validation memo (`tests/test_track1_memos.py:50-122`):** Verified by in-memory mutation testing that breaking any of the four key components (`validate_package.__code__`, `package_digest`, `members`, `schema_digest`), removing `copy.deepcopy` on hit, removing `copy.deepcopy` on store, or disabling `_VALIDATION_MEMO_LIMIT` eviction causes `ValidationMemo` to fail. (See `RKE-R2` regarding `corpus` and `marshal.py`.)
- **Closure-walk memo (`tests/test_track1_memos.py:127-320`):** Verified by in-memory mutation testing that making `memo` persist across calls or dropping the `family_id` filter in `meaning_for` causes `ClosureWalkMemo` to fail (19 and 18 test failures respectively), and `test_shared_blocked_rows_are_walked_once` exercises a 40-layer diamond ($2^{40}$ unmemoized paths). However, removing `frame.hits.isdisjoint(seen)` or `seen.isdisjoint(known.examined)` does not fail the current 1,500 random graphs (`RKE-R1`).
- **Source-family index (`tests/test_track1_validation_index.py:38-80`):** Pins the exact issue count, sorted issue multiset digest, `resolved_members` digest, and `output_owners` digest from pristine commit `0763f572` across published `v96` and four invalid mutations.
- **Honesty of `live` markers:** Honest. `tests/test_track1_validation_index.py` loads the 7,252-file published corpus and runs 5 full package validations (~11–16 s, exceeding `FAST_LANE_BUDGET_SECONDS = 3.0`), so its explicit `pytestmark = pytest.mark.live` and docstring rationale comply with `tests/conftest.py:168-169`. `tests/test_track1_memos.py` is unmarked, uses synthetic `demo.*` fixtures only, and runs in ~0.25 s in the fast lane.

### 5. Conclusions

- **Support for Decisions 1–2 and the kernel-port conclusion:** Strongly supported by both P0 and Track 1 measurements:
  - In P0, the kernel (`findings.project` plus `facts.py`) accounted for ~6 % of the median recorded replay (`0.37 s` of `6.6 s`) and ~1 % of the slowest (`0.43 s` of `39.2 s`), while algorithmic loops in `packages/derivation/` (`validate_package`'s $O(F \cdot M^2)$ scan and `presentation_projection._closure_question_reasons`'s unmemoized path walk) accounted for ~57 % of the median and ~84 % of the slowest list.
  - In Track 1, fixing those derivation algorithms in Python reduced total replay CPU across all 775 recorded lists from `5,853 s` to `2,026 s` (`2.9x`), parallel wall time from `787 s` to `278 s`, single-process median replay from `6.73 s` to `2.61 s`, and single-process slowest replay from `38.49 s` to `2.69 s` (eliminating the 28-list tail above 10 s), with zero kernel edits.
  - Post-Track 1, `findings.project` on a median recorded list is `0.44 s` out of `2.57 s` (~17–20 % inclusive), of which `0.23 s` is `facts._lattice_metadata` (itself an algorithmic scan per assertion) and part is `SchemaRegistry.validate` (`jsonschema`). Even a zero-cost Rust kernel fold could save at most ~`0.44–0.50 s` per recorded replay, whereas Python file I/O and JSON loading/hashing in `production_resolver._json_candidates` (reading 7,252 member files 4 times per replay: `0.67 s` plus `citizen_checksum`) is now the largest remaining cost (~40 % of wall). On K13-shaped recorder stories (`5.01 s`, `51` full log projections, `2.75 s` in `findings.project`), the dominant cost is also algorithmic (full re-projection on every save and per-assertion `_lattice_metadata` rebuild).
- **Is anything overstated?** No. Note that P0's rough estimate (`6.6 s` to `~1.5 s` on the median list, `p0.md:109, 323-325`) included `~0.7 s` for memoizing `_json_candidates` file reads, which `charter-track1.md` left out of scope; `track1.md:132-133, 210-226` explicitly accounts for that remaining file-I/O share rather than overstating the saving.
