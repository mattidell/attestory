# P0: blocked lines name their question

Date: 2026-11-12. Published baseline: core v87, package registry v85,
release v85. The scratch package calls itself v88 only inside the evidence
directory; production must use the next version free after the parallel
age-blindness milestone.

## Result

The defect is reachable on v87. All ten filer-facing cases complete a live
coordinate run, leave at least one page field blocked, and show zero question
sentences. The four internal-subtotal probes also complete, but no filer field
is blocked by their open subtotal alone. They are not part of the repair.

The smallest repair is one additive rule-artifact successor: an expression
`block` may carry the `missing` names its selected refusal waits on, and the
evaluator records those names unchanged. Two boundary facts also need ordinary
input-question citizens. The wash admission needs a content-only rule
successor which reads the already-published adjustment-family closure check
before it attempts per-transaction pairing. This needs no kernel change and
does not change which answer any path needs.

The scratch successor makes a question visible in every filer-facing case.
The exact 775-list recorded-return replay is reported below.

## Trace

1. The expression is the loss point. Rule-artifact v16's top-level fallback
   already has `blocked.missing`, but an expression `block` permits only `op`
   and `code` (`packages/schemas/derivation/rule-artifact.v16.schema.json:626-641`).
   The evaluator therefore raises `EvalBlocked(expr["code"], [])`
   (`packages/derivation/evaluator.py:507-508`), and the runner faithfully
   records that empty list (`packages/derivation/runner.py:2531-2549`).
2. The reachable rules use that expression shape at the decisive branch:
   Schedule D line 3 (`packages/content/tax/2025/rule.schedule-d-line3.v2.json:194-197`),
   code-B short-term gain (`packages/content/tax/2025/rule.f1099b-code-b-st-gain.json:209-212`),
   and the no-1099-B amounts check
   (`packages/content/tax/2025/rule.f8949.no1099b-st-txn.amounts-check.json:45-63`).
   Their long-term or code-B twins have the same shape.
3. Projection is working as designed. It indexes closure and input questions
   from adopted citizens (`packages/derivation/presentation_projection.py:508-528`),
   walks a line's missing names through blocked producers
   (`packages/derivation/presentation_projection.py:565-633`), and emits
   nothing unless every terminal cause is explainable. An empty expression
   list gives it no root. The Path-B fact reaches the projection, but v87 has
   no input-question citizen for that fact.
4. The wash case has one explainable root: the v4 closure mapping already
   declares the adjustment-family question
   (`packages/content/tax/2025/closure-mapping.f1099b-covered-w-st-adjustment.v4.json:1-22`).
   The admission-check path first runs three `require_paired` guards
   (`packages/content/tax/2025/rule.f1099b.covered-w-st-txn.admission-check.v2.json:44-70`).
   Its second root is therefore a keyed transaction identity with no input
   question. Projection's all-roots rule correctly suppresses the partial
   explanation.
5. The four internal subtotals already name their open families. Their probes
   block no presentation field, and their v2 closure mappings declare no
   filer question. Adding questions for them would create a new UI obligation,
   not repair a reachable dead end.

## Design comparison

### Content-only on rule-artifact v16

Adding input-question citizens fixes the two boundary facts
`schedule-d-boundary.no-form8949-sources` and
`schedule-d-boundary.no-other-form8949-adjustments`. It cannot repair an
empty `missing` list, because the projection has no name to join to those
citizens. A v16 rule can sometimes move a closure check into a selected
path—as the wash prototype does—but the amount-disagreement and selected
refusal branches have facts present and invalid. Recasting them as absent
dependencies would misstate the refusal and risks changing evaluation order.

### Rule-artifact successor

An expression-level declaration is local to the branch that refused, retains
its existing code, and supplies only explanation-routing names. The prototype
uses this shape on ten rule successors: Schedule D lines 3 and 10; short- and
long-term code-B gain; the two no-1099-B amount checks; the two code-B amount
checks; and the two covered-wash admission checks. It also adds the two
question citizens above. `prototype-build.json` records the package shape;
`prototype-output.json` records all 14 results.

The wash successors additionally ref the existing adjustment closure check in
the active `sales` path and keep the old admission expression behind that ref.
When the family is closed the original expression runs unchanged. When it is
open the path names the existing closure question instead of a keyed
transaction that the filer cannot answer.

## Draft ADR Decision text

> Introduce the next `rule-artifact` schema version as an additive successor
> to v16. An expression whose `op` is `block` may declare `missing`, a
> non-empty array of unique, non-empty names. When that expression is selected,
> evaluation raises the expression's existing block code and exactly the
> declared names. If `missing` is absent, behavior remains the existing empty
> list. Declared names are explanation routing: they do not add reads, pins,
> scheduling dependencies, source-family authority, or answer semantics.
> Existing rule-artifact versions remain byte- and behavior-stable. Published
> packages use declared names that resolve through their adopted question
> citizens or closure mappings whenever a filer-visible field can reach the
> block.

This is a rule-language contract and needs an accepted ADR before Track 1.
It is a derivation schema/evaluator change, not a kernel change.

`rerun.py` materialized the question-wording Track 0 neighbour set once and
split that exact serialization across CPU-count-minus-one subprocesses. Nine
shards ran all 775 distinct act lists once on v87 and once on the scratch
successor: 1,550 live runs in 1,794.553 seconds.

The 69 predecessor “numbers changed” candidates differed only under `rows.*`,
where the successor records a non-empty `missing` list; every watched line
value diff was empty. The other 25 changed only question/reason fields. No new
question appeared on a return that computed before (`0/775`). V84's 58 and
v85's 43 lists are all byte-for-byte identical at the pin; earlier blocked
fixtures account for the intended explanation changes. `rerun-output.json`
contains a class for every recorded id and the details of all 94 changes.
