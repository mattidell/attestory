# P0: where the time goes on published core v96

Milestone: rust-kernel-experiment. Stage: P0 (profile, no code change).
Source: branch milestone/rust-kernel-experiment-2025 at `47f4ccad`
(core v96, registry v94, release v94). Machine: 10 CPUs, Python 3.14.
Nothing under `packages/` or `tests/` was edited. Every number below is
read from the JSON files named next to it, in this directory.

## Answer in one paragraph

The kernel is not where recorded replays spend their time. On the median
recorded list the kernel (act projection, fact lattice, finding model)
is about 6 % of wall time; on the slowest list it is about 1 %. The
dominant costs are algorithmic and sit in `packages/derivation/`:
package validation re-walks the whole member list for every source
family on every run (about 50 % of the median list), and the
presentation projection's closure-question walk enumerates paths through
the blocked-row graph without memoization and rescans the resolved
members on every step (84 % of the slowest list). Each has a plain Python
fix. The kernel does dominate one shape of work, the recorder-built
correction stories in the test suite (K13: 52 % in kernel projection),
and there the cost is also algorithmic: every save re-projects the whole
log, and every assertion rebuilds the lattice metadata over every fact
type. A Rust port of a kernel slice would save at most about 0.4 s of a
6.6 s median replay. The recommendation is to fix the algorithms in
Python first and re-measure before any port.

## 3. Shape of the cost

**Slowest list, prefixes of its recorded act log** (`p0-prefix-slowest.json`;
census finish and handover appended to each prefix, one process):

| Prefix | Acts run | Assertions | run_s | total_s |
| --- | --- | --- | --- | --- |
| 10 %, 25 %, 40 % | — | — | refused by the SSA handover (no SSA facts yet) | — |
| 50 % | 177 | 101 | 7.5 | 10.2 |
| 60 % | 211 | 121 | 7.2 | 9.7 |
| 75 % | 263 | 159 | 7.7 | 10.2 |
| 85 % | 298 | 172 | 7.4 | 10.0 |
| 90 % | 315 | 175 | 25.9 | 28.5 |
| 95 % | 333 | 177 | 37.8 | 40.5 |
| 100 % | 350 | 181 | 36.3 | 38.9 |

Run time is flat in log length from 50 % to 85 % and then jumps 3.5x
between 85 % and 90 %, when the code W sale rows arrive and the blocked
rows go from 315 to 319. The cost is superlinear in the shape of the
blocked-row dependency graph, not in the number of acts. The loop is
`_closure_question_reasons.reach_mixed`
(`packages/derivation/presentation_projection.py:565`, recursion at
:580): `seen` is the current path, not a visited set, so a row reachable
by many paths is re-walked once per path (1.31 M `reach_mixed` calls for
40 lines on the slowest list, 0.31 M on the median). Each step calls
`meaning_for` (:535), which scans every resolved member (:547-548) and
rebuilds `_constraint_meanings` (:416, a full recursive `walk`) for the
match: 1.89 M `meaning_for` calls, 39 M `walk` calls, 587 M `dict.get`
calls.

**Kernel projection alone, prefixes of the same finished log**
(`p0-kernel-growth-slowest.json`; `findings.project` with the registry
`live.py` builds, best of three):

| Acts | Assertions | Fact types | project_s | ms per act |
| --- | --- | --- | --- | --- |
| 35 | 14 | 30 | 0.003 | 0.08 |
| 105 | 46 | 103 | 0.024 | 0.23 |
| 175 | 101 | 199 | 0.061 | 0.35 |
| 245 | 151 | 296 | 0.112 | 0.46 |
| 315 | 175 | 353 | 0.177 | 0.56 |
| 350 | 181 | 403 | 0.210 | 0.60 |

One projection is superlinear (time per act rises linearly with the
number of fact types; doubling 175 to 350 acts costs 3.4x, exponent about
1.8). The loop: for every assertion, `_CurrentLatticeHolder.for_state`
(`packages/kernel/findings.py:734`) calls
`facts._current_lattice_for_replay` (`facts.py:667`), whose `view`
(`facts.py:555`) recomputes `_lattice_metadata` (`facts.py:449`), a tuple
over every fact type and every entity, then compares it with the last
one. The function's docstring records the choice ("No identity-only
shortcut ... These metadata scans are growing costs"). At replay scale
this is still 0.2 s. In a recorder story it compounds: each save
re-projects the whole log (K13: 51 `project` calls over a log growing to
268 acts, 12351 metadata rebuilds), so the story is roughly cubic in its
length.

## 5. Port candidate

**Slice.** The kernel replay fold: `packages/kernel/findings.py`
`project` (:1703), `_apply_project_act` (:1686), `_apply_assertion` (:863),
the lattice holder (:727), and in `packages/kernel/facts.py` the lattice
construction `_lattice_metadata` (:449), `_LatticeProduct.view` /
`view_metadata` / `update` (:555-:600) with `_add` and `update_axes`
(:486, :514), `_project_fact_lattice`
(:315) and `_fact_id` (:299). That is where all of the kernel's own time
in the three profiles sits (fact store 6.3 / 1.4 / 54.8 % own).

**Data crossing per call.** In: the whole act tuple (dicts of JSON
values, 300 to 400 acts per replay) and the registry's admission maps
(companion presence and equality pairs, declaration-signal
contradictions, supersession declarations). Out: a `FindingState`
(findings, evidence, the `KernelState` with fact types, entities,
retired ids) that the derivation layer reads as Python objects
(`compute_currency`, `validate_projected_source_boundary`, marshal,
presentation). Either the whole state is converted back to Python per
call, which at 180 findings and 400 fact types costs the same order as
today's 0.2 s projection, or the state stays in Rust behind accessor
methods, which touches every reader in `packages/derivation/`.

**Coupling that makes a binding costly.** `_validate_finding`
(`findings.py:745`) calls `registry.validate` (jsonschema, in Python) per
assertion; admission and supersession invariants (`findings.py:261-725`,
`1463-1550`, `1965`) read registry maps and raise Python
`FindingModelError` with specific messages that tests match. A Rust fold
must call back into Python for schema validation per act (keeping a
boundary crossing per assertion) or reimplement JSON Schema validation
for the admitted schemas. The `_REPLAY_LATTICES` context variable and
weak-reference memos in `facts.py` (:340-:430, :647-:690) tie lattice
identity to Python object identity.

**Checking byte-identical.** Track 2's existing harness covers it: for
all 775 recorded lists, run both paths and compare `pin_sha256` (rows and
publications, as `p0_workload.run` computes) and page bytes; in addition,
compare a canonical JSON dump of the `FindingState` (findings, evidence,
fact lattice ids, currency) for every prefix of every finished log, and
the error class and message for the 84 lists that error.

**What it does not cover.** Package resolution and validation, the
closure-question walk, marshalling, the evaluator, presentation,
jsonschema, JSON and file I/O: together 90 % or more of a recorded
replay. Its upside on replays is bounded by the 0.37 s it can remove
from a 6.6 s median (under 6 %), and on the slowest list under 1.5 %.
On recorder stories like K13 it would capture more (up to about half),
but an incremental Python fold removes the same quadratic term.

## Recommendation

Do not port yet. P0 shows the algorithmic fixes dominate, which is the
case stage 2 of the plan anticipates: recommend them first. Four Python
changes in `packages/derivation/` (validation index and memo, file-load
memo, closure-walk memo and member index, marshal precompute) should take
the median replay from about 6.6 s to about 1.5 s and the slowest from
39 s to about 2 s, with no kernel edit. A separate kernel change
(incremental re-projection on save and a generation-keyed lattice
metadata cache) addresses the recorder-story cost. Re-profile after
those; if the owner still wants the Rust experiment for language reasons,
run it against the post-fix baseline, where the kernel fold would be a
larger share and the speed claim honest.

## Decisions for the foreman

1. Redirect or continue. Owner decision: open a Python algorithmic track
   (derivation-side fixes, no kernel edit, outside this milestone's
   current scope) before any port, or continue the Rust slice as an
   experiment for language and agent-fluency evidence with the speed
   upside known to be under 6 % per replay today.
2. If the port continues: the slice is the kernel replay fold named in
   section 5; gates 2a (governance read on implementation language and
   the kernel boundary) and 2b (owner confirms the `packages/kernel/`
   edit) are still open. The schema-validation callback per assertion is
   the design question Track 1 must answer first.
3. Whether to also charter the kernel algorithmic fix (incremental
   re-projection, lattice metadata generation) that the facts.py
   docstring deliberately declined; it needs the same kernel-edit
   confirmation as the port.
4. Evidence tooling: replay harnesses validate the same package twice
   per list (prep's SSA handover plus the run); a checksum memo in the
   harness would roughly halve replay CPU even before production fixes.
   That is a `tools/` change only.

outside the repository.

```sh
  python3 $D/p0_profile.py centres $w <scratch>

```
