# P0 evidence — Name the sale on the saved question

The current sale entity can name a Box C or F sale. The projection can identify
the sale from the existing question walk and the findings the engine already
read. Core v109 reaches six adopted questions across three kinds: proceeds,
basis and wash-sale adjustment. The scratch proof adds the recorded name to
the saved explanation, preserving the engine output and the question's
existing answer link where one exists.

## Question inventory on core v109

| Form 8949 question | Blocker that makes the walk reach it | What the saved page shows today |
| --- | --- | --- |
| Box C or F, column (d), net proceeds | Schedule D line 3 or line 10 v3 runs `require_paired` on `sale`. A whole-sale finding has no matching proceeds finding. | One plain, unnamed question for the term. A missing scalar can have no existing question group. |
| Box C or F, column (e), cost or other basis, missing amount | The same rule and pairing, for the basis scalar. The proceeds check comes first. | One plain, unnamed question for the term. |
| Box C or F, column (e), cost or other basis, consistency check | The term's `amounts-check` v2 reads per-sale `amounts-agree` v1 results and blocks on a disagreement. It names basis even when the disagreement came from a proceeds row or from a missing wash-sale adjustment. | The same basis question. The example has one unnamed reason and no linked answer group. Labelling identifies the sale whose amounts disagree. The existing rule still does not identify the disagreeing column. |
| Box C or F, column (g), wash-sale loss disallowed | The walk reaches the family's synthesized validation block and its adopted fixing question for `CODE_W_ON_GAIN` or `ADJUSTMENT_EXCEEDS_LOSS`. Both codes can arise for one sale. | The declared explanation or explanations and one adjustment question reason for the term, with existing links to the violating sales' adjustment groups. The line shows the question link above rather than a named reason. |

## Recorded naming data

| Candidate | Where it lives and what the projection can use |
| --- | --- |
| Sale label | `entity.v1.label` on the current `tax.us.f8949-sale` entity. The whole-sale and scalar facts both carry the exact `sale` entity key and literal `tax-year` key, so the label is reachable through the evidenced sale identity. |
| Description | The v1 no-1099-B whole-sale findings have a closed value shape with `proceeds`, `basis`, `long_term` and `wash_disallowed`. There is no description slot. A description the filer chose as the entity label is usable as that label. |
| Acquired and sold dates | Neither date is an adopted Box C/F input read by these rules. The whole-sale finding stores a holding-term flag. The closure question about whether sales occurred supplies family closure, not sale dates. |
| Sale ID or evidence label | The entity ID joins findings and distinguishes identities. It is technical metadata. An evidence label names evidence that may support several findings. |

The recommended cohort is all distinct current source-backed Box C/F sale
entities on this 2025 return. A sale whose question is answered still counts
as a peer. A current entity with no current whole-sale finding supplies no
peer. With only one sale, today's reasons stand. A name is usable if it is
nonblank, different from the entity ID and unique among current peers after
case-folding and collapsing whitespace. The scratch displays the recorded
spelling and spacing. If a targeted label is missing or repeated, that sentence
keeps its existing generic reason or question links. A repeated label on an
answered peer also prevents displaying that label. With several targets for
one sentence, the scratch requires all their names before expanding the
sentence. No ordinal is inferred from entry or finding order.

## Route and scratch proof

Capture the evidence at the leaf that the ordinary question walk already
reaches, then use one of the following routes.

1. **Missing proceeds or basis.** Use the exact Schedule D line 3 or 10
   pairing declaration. Replay the evaluator's shared `paired_coverage` test
   on the current source and scalar assertion pins. Only uncovered sale
   keys qualify. An answered peer's scalar pin is required for the replay.
2. **Basis wording from the consistency check.** Use the pinned
   `amounts-agree` publications with value `disagree`. Require the published
   disposition with the matching subject suffix and the pinned current
   whole-sale finding. This route consumes the published result and does
   no new amount comparison.
3. **Wash-sale fixing question.** The validation blocker carries the family
   and violation code but no per-member input pin. Read the sibling synthesized
   member-validation publications, match the reached code, and follow each
   publication's exact current whole-sale pin. Require complete coverage of
   current sales for that family. A sale violating both codes yields one name
   on the question.

Resolve `sale` and `tax-year` from the structured current facts. Deduplicate by
sale identity and sort each expansion by recorded label then canonical
identity. An unlinked generic reason becomes one display-only reason per
proved sale. A linked reason stays at its place and the named reasons follow
it. Adjust indices so the same references still point at the same original
reasons. The display reason has `sentence` and `saleLabel`. Its name is rendered
as text before the unchanged question. The saved v3 schema allows the reason
payload and the scratch runtime validator admits only this two-field shape.
The scope of the annotation excludes the family explanations themselves.

The scratch overlay loads the projector and page by Git blob from the
ratified merge `0172559abe564a0dc9da0aea521d4dd419e05d8f`. It confirms ancestry
against `HEAD`. This baseline is already in main's history and the scripts
require no remote-tracking ref. The overlay runs in memory and writes the
renderer and live outputs to temporary directories outside the tracked tree.

## Trusted inputs and controls

The projection-input controls mutate copies of arguments from actual
`live_coordinate_run` calls. A mutation that invalidates an identity, route or
witness suppresses the sale name. Some corruptions would already be refused by
admission. [Executable controls](trusted_inputs.py)

| Input | Removal or corruption |
| --- | --- |
| Selected core, original question leaf and adopted answer fact type | Exercise published v108 end to end. Remove the adopted question or its sentence, change the question pin in a projected v110 successor, or add a second unexplained source of the same sentence. Change the package ID, block disposition, code, or leaf. |
| Exact and current sale/answer identities | Omit projected currentness, remove current sale support, change the year or one of the two identity contracts, or introduce a second current finding for the same sale. |
| Current sale entity and distinguishable label | Displace the entity, change its kind, remove or blank the label, substitute the technical ID, or repeat the label on a target or valid peer. The synthetic replay also covers differently cased and spaced duplicates, one sale, and no blocked sale. |
| Adopted pairing and all current source/answer pins | Remove the pairing rule, change its join key in the successor control, remove a whole-sale or answered-peer pin, or substitute an unknown pin, incorrect pin version or origin. |
| Term's amount-check producer, per-sale disposition, publication and value | Change the adopted amount-check rule version on the successor control, change the subject declaration, remove or corrupt the derived input pin, remove or retarget the disposition, or remove the publication or corrupt its symbol or categorical value. |
| Adopted family and reached fixing code, member validation witnesses and current sale pin | Change the member predicate or fixing question pin, remove the block's code or a validation publication, alter the member identity or the violation list, or remove the witness's sale input pin. |
| Final reason order and link semantics | Remove a name, swap two names, replace a name on an unlinked reason, add a name to a repeated-label reason, or move a linked question reference onto a display-only reason. |

`v110` is an unpublished projection input in the mutation probe. The probe
reuses the actual v109 resolved members and runner evidence with the advanced
package version, then changes the individual contracts in separate controls.
It demonstrates acceptance under the same contracts and fallback when they
change. It covers neither loading nor executing a successor content package.

## Full-surface replay

The replay compares the base and scratch saved models and reports through the
live coordinator, using the same run ID on both sides. It asserts the exact
sale name and reason index against fixed synthetic expectations and the
recorded expectation of zero additions. For linked reasons it expects the
original references at their shifted indices. It counts changed lists and
checks typed structural equality of everything else, including all report
rows, amounts, dispositions, pins and active codes. For a failed save it
compares the outcome, error class and the replay tool's path-masked message.
It executes the real saved-page script in the repository's DOM harness to
check the exact ordered name prefixes on named synthetic sections.

## Proposed amendment to ADR 0089

Status **proposed**. Owner disposition is required before Track 1.

1. On core-calculations v109 and successor cores retaining the declared
   routes and identity contracts, a saved question about a Box C or F sale
   may display the recorded label of that sale when the return contains
   multiple current source-backed no-1099-B sales. Use the complete
   `sale`/tax-year identity. The label is presentation text.
2. Attribute only a question reached by the existing walk. Use the shared
   pairing test over the block's current source/answer pins for missing basis
   or proceeds, the pinned per-subject disagreements for the existing basis
   consistency question, and the same-family, same-code member validation
   publications and current source pins for the wash-sale fixing questions.
   Where more than one witnessed leaf reaches a sentence, require proof
   from each leaf.
3. Use the matching current sale entity's nonblank, distinguishable recorded
   label. Compare labels across all current Box C/F sale peers, including
   answered peers, with case and whitespace normalized for collision
   detection. Preserve recorded spelling and spacing in the display.
   Keep the existing reason for a sentence if any of its targets cannot
   be identified and named uniquely. Keep the existing single-sale display.
4. Show one `saleLabel` display reason per identified sale and sentence,
   sorted by recorded label and canonical identity. Retain an existing
   linked reason before the new reasons and shift references to their original
   targets. Keep question text and groups, answer scopes and targets, numbers,
   dispositions, block codes, report rows, pins and existing statement and
   roster labels. The saved page supplies display only.

## Owner decisions

- Accept the amendment before Track 1. In particular, select the multiple-sale
  floor and whether missing or repeated labels should keep the generic
  display for the whole sentence.
- Confirm that a consistency block may name the sale with a published
  disagreement beside the already-adopted basis question. The scratch
  evidence shows why this wording can be misleading where only proceeds or
  adjustment differs. Selecting more precise wording is a separate content
  decision.
