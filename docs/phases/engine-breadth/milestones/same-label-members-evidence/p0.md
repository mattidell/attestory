## Result in one paragraph

On v107, when two or three members of one roster carry the same recorded
label, the saved page merges them. Two children named "Demo Sam", both missing
the age answer, get one reason ("Demo Sam: Does this child meet the age
test...") on each of the 9 lines it blocks, where two answers are missing.
When the two are missing different answers, the page shows two reasons, both
headed "Demo Sam", and the filer cannot tell which Sam each is about. When
only one is missing, it shows "Demo Sam" and the filer cannot tell which. The
merge is one line: the walk records each member's question as
`(fact type, label)` and the reasons are built from that set, so two members
with one label collapse. The scratch change keys the set by the member's
subject keys instead, and adds one optional reason field, `memberOrdinal`:
present only when another current member of the same kind has the same
label, it gives the member's position among them in the order the workspace
added them. The page shows it as "Demo Sam (the second one you added with
this name)". On the 23 probe returns each member now gets its own reason and
the filer can tell them apart; distinct labels and a child and a parent who
share a label are unchanged. The full-surface replay is 775 of 775 recorded
lists identical (691 success/success, 84 error/error on both sides); the 17
probe lists that differ differ only in page reason entries. No number,
disposition, block code, report row, graph node or question link changes.
**Recommendation: the keying fix brings the code into line with ADR 0087's
"one reason per member", but telling same-named members apart needs a reason
field ADR 0087 did not decide. A proposed ADR is drafted
(`adr-draft.md`); stop for the owner.**

section errors and no first-read leaks.

**No member reason links a question group, before or after.** None of the 23
saved models has a question group (`questionGroups` is empty and no group's
answer target names a member), and no member reason is in any line's
`questionRefs`. This is ADR 0087 Decision 3 as built: the projection skips
member reasons when it indexes reasons for links
(`presentation_projection.py:1094-1097`, "A member's question (ADR 0087) is
explanation only; it links no group"). The plan's "links its question group"
therefore has nothing to link today; giving member questions groups would
change their answer target, which is a non-goal.

**Empty labels cannot occur.** `entity.v1` requires `label` with
`minLength: 1`, so a member always has a non-empty recorded label. The
roadmap's "an empty or repeated label" reduces to a repeated one.

## 2. Where reasons merge (file:line, this commit)

- The walk records a member question as `(fact type, label)`:
  `frame.member_facts.add((subjects[0], label))` at
  `presentation_projection.py:1028` and `frame.member_facts.add((key, label))`
  at `:1038`, with `label = roster_members.label(keys)` from `:1003`.
- The set is `member_facts: set[tuple[str, str]]` (`:733`, `_WalkFrame`
  `:1430-1447`), so two members with one label and one missing fact type are
  one element.
- Reasons are built from the set, deduplicated again by `(label, sentence)`:
  `:1061-1064`.
- `_RosterMembers.label` (`:611-621`) returns the label of the one current,
  labelled entity named in the member's keys, or None; that None keeps a
  member with no single label silent (ADR 0087 Decision 3) and is unchanged.
- The other sentence dedupes are not on this path: the statement dedupe in
  `_selection_blocked_reasons` keys on statement identity (`:309-331`), and
  `_missing_mentions` (`:453-465`) only finds a token.
- The page draws every reason it is given; it does not dedupe them
  (`citation-walk.v1.html:1459-1464`). `tools/sale_page_observation.py:717`
  mirrors the page's reason prefix and would need the same ordinal text.

## 3. Label source and what else could tell members apart

The recorded label is the member entity's `label` (`entity.v1`: `id`, `kind`,
`label`, nothing else). Routes considered:

| Route | Tells same-named members apart? | Invents a name or shows an id? | Changes ADR 0087? |
| --- | --- | --- | --- |
| A. Key by member only, no new field | No. Two identical "Sam: age" lines say two answers are missing but not which Sam is which; with one missing, still "Sam" | no | No (it is what Decision 2 already says) |
| B. Compose an ordinal into `memberLabel` ("Sam (2)") | Yes | `memberLabel` would no longer be the recorded label | Yes: Decision 2 defines it as the recorded label |
| C. Another recorded attribute the filer entered | No such attribute: an entity has only id, kind, label. Per-member answers are not identifying and may be the missing ones | ids are forbidden | n/a |
| D. Page-side numbering of repeated labels | No: the page sees only the reasons on a line; with one Sam missing, it cannot know there are two | no | No |
| **E. Key by member, plus `memberOrdinal`** (scratch) | **Yes, on every line, including when only one is missing** | no: a position in the order the filer added them | **Adds a reason field Decision 2 did not decide** |

Route E's ordinal is computed from the recorded workspace only: among the
current entities with the member's `kind` and `label`, in the order the
workspace introduced them (the kernel's entity map is built in act order,
`packages/kernel/facts.py:185-189`; a successor entity is added at the end,
`:217-219`). It is absent when the label is unique within the kind, so every
return with distinct labels is byte-identical. Same-kind only: a child and a
parent named "Sam" are asked different questions, and peers of other kinds
(an employer, a statement) never count.

## 4. Scratch proof

`scratch-projection.diff` changes three definitions: `_RosterMembers` (a
`_member` helper; `label` unchanged in meaning; new `ordinal`),
`_closure_question_reasons` (member questions keyed by subject keys; one
reason per (label, ordinal, sentence), sorted that way; `memberOrdinal` only
when there is one) and `_validate_resolved` (accepts `memberOrdinal`, a
positive integer, only beside `memberLabel`). `scratch-page.diff` adds the
ordinal to the bold prefix: "Demo Sam (the second one you added with this
name): ...". The `presentation-model.v3` JSON schema does not constrain reason
entries, so no published schema file or version changes; the projection's own
validator is what admits the field.

## 5. Full-surface replay

`replay.json` (`replay.py`). One shared `recorded_replay.replay` run, 8 pool
workers, on v107: every list taken twice, repository projection then scratch
projection, compared with `classify_full` and no expectations. It ran in two
foreground passes over one resumable part file (about 10 minutes, then the
remaining 60 lists); the summary's `wall_time_s` is the second pass only.

- **Recorded lists: 775 of 775 identical**, 0 differences. Outcomes:
  691 success/success, 84 error/error (the same admission errors on both
  sides).
- **Probe lists:** 6 identical (the four controls with distinct labels or
  no missing answer, and the child-and-parent case), 17 differ, 688
  differences, all on page reason entries: `memberOrdinal` added (327),
  `memberLabel` and `sentence` added for the second and third members (111
  each), `resolved.reasons@order` (101) and `sentence` (38) where the
  ordinal sort reorders a line's reasons. No other kind or attribute.

So no number, disposition, block code, report row, graph node, attachment or
question link changes anywhere in the corpus, and the recorded corpus has no
return with two same-named members on one roster.

## 6. Recommendation and decisions needed

1. **Route E, recorded as a proposed ADR** (`adr-draft.md`). The keying fix
   alone is a repair to ADR 0087 Decision 2 ("one reason per member"), but on
   its own it leaves the filer unable to tell the members apart. The ordinal
   is a new reason field a later artifact (the page, the sale observer, any
   UI) is written against, which ADR 0087 Decision 2 ("one new optional
   reason field, `memberLabel`") did not decide. Owner decision: accept the
   ADR, or direct that this fits within ADR 0087.
2. **Ordinal basis**: position among current same-kind, same-label members in
   the order they were added. A member replaced by a successor entity moves
   to the end (not probed). Owner decision: accept entry order, including
   that effect.
3. **Page wording**: "Demo Sam (the second one you added with this name)",
   English ordinals to tenth, "number N" after. Owner or foreman decision on
   the words.
4. **Fallback if the ADR is declined**: Route A only (one reason per member,
   no ordinal), which needs no ADR but leaves duplicate-looking lines.
5. **Not in scope, recorded**: member questions still link no question group
   (ADR 0087 Decision 3); "empty label" cannot occur (`entity.v1`).
