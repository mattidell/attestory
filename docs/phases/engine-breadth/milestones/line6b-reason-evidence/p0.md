## Result and reproduction

A truthful wage-plus-SSA filer can leave worksheet scope questions unanswered
and receive a blocked line 6b with only the generic instruction:
“line 6b is blocked because a worksheet or source dependency is incomplete.”
There is no reason/question sentence for ten terminal names. Unlike the
parked report, **none of these worksheet rows has an empty `missing` list**.

`probe.py` uses the wage/SSA construction from the page-alerts precedent,
loaded on this branch from `github/milestone/page-alerts-2025`, and the
question-wording wage harness. Harness modules are imported by file under
unique names. Every case goes through `live_coordinate_run` and the actual
presentation projection. We read all `resolved.reasons` sentences and the
field's disposition instruction; no punctuation filter is applied.

The wage return has wages 50,000 and W-2 withholding 4,500. Its one ordinary
SSA-1099 has box 3 and box 5 12,000, box 4 zero, ordinary statement kind,
taxpayer recipient, and the required false election witness. Taxpayer and
spouse age and blindness are stated false. SSA box-6 payments are not needed
to evaluate line 6b; these cases do not claim a fully answered payments section.

The 168 distinct cases cover single, joint and separate filing; all 23 scope
facts yes together, each no and each unanswered; living arrangement no and

## Design comparison and prototype

| Alternative | What it gains | Cost or limitation |
| --- | --- | --- |
| Ten question citizens, adopting each as a member and entrypoint | Repairs every reproduced line-6b reason; no rule or answer change | A fact-global question also reaches other blocked fields, including line 6d on a computing return |
| Worksheet successor on rule-artifact v17, declaring block names | Useful when an expression block has an empty list | No such loss here; the ten names are already exact. Adds a rule version and provenance churn without controlling question placement |
| Only the original line-24z question | Repairs the original wage/SSA harness case | Leaves the other nine plan-reachable missing names unexplained |
| Omit the living-arrangement question | Avoids the new line-6d prompt | Leaves the reproduced separate-filing line-6b block unexplained |
| Change line 6d's rules to bypass the answer on no-benefit returns | Could hide that prompt | Changes an existing answer/disposition requirement, explicitly outside the charter |
| Field/branch-aware question placement | Could preserve both the line-6b explanation and the no-new-question target | Requires a projection change, potentially declarative question-schema support; overlaps blocked-sale-pages and triggers the stop condition |

`prototype.py` builds a scratch core v92 on published v91 using
`tools.package_successor.generate_to_directory`, a checksummed registry and
release. It copies published content into a caller-selected scratch directory;
no file in `packages/` is edited. Ten input-question citizens and their
entrypoints are the only content additions. Rule bytes, input bindings,
required answers, refusal codes and numerical content remain unchanged. The
first build correctly refused unrooted question members; adding the same
entrypoint declarations that published input questions use resolved that
package validation error. `prototype-build.json` records the final build and
has no inherited validation inconsistencies. Scratch version numbers reserve
no production versions.

`check_prototype.py` runs all 168 lists against the scratch core, using the
already-measured baseline except for three new combined-absence cases. It
compares line-6b values, dispositions, active codes, field instructions,
worksheet rows and the blocked producer walk. **134 identical; 34 change only
reason sentences; zero unexplained line-6b blocks; zero unexpected state
changes.** Every formerly reasonless block now names its actual question(s).
`prototype-output.json` retains every resulting sentence. This proves the
content mechanism for line 6b, not compliance with the computing-neighbour
target described below.

## Computing neighbour and stop condition

`computing_neighbours.py` compares **every page field's disposition and value**,
and all reason sentences, on seven current wage neighbours on both cores
(31.201 seconds, 9 workers). Three no-benefit returns with complete current
answers compute refunds: single 625, joint 2,647, separate 625. They gain no
question. Three SSA neighbours publish line 6b 10,200 but still block payments
because their real box-6 withholding amount is not recorded; they are not
counted as fully computing returns. Their page states and questions also
remain unchanged.

The seventh neighbour is a separate filer with no benefits and the living
arrangement unanswered. **It already computes on v91:** line 6b is zero,
refund 625, balance due zero. On the scratch successor every field value and
disposition remains identical, but both `form1040.line-6d` and
`form1040.line-6d-not-checked` acquire:

> If you are married filing separately, did you live apart from your spouse for all of 2025?

The two existing line-6d rules require this fact whenever filing separately,
without an SSA-presence condition (`rule.form1040-line6d.json:40` and
`rule.form1040-line6d-not-checked.json:40`). Adding a question for the shared
fact makes the global projection index attach it to both. This is **one
computing return newly asked one distinct question on two fields**. It changes
no required answer, number, refusal code, or field disposition, but it fails
the charter's no-new-question target.

To meet both targets without changing those existing answer requirements,
the smallest additional seam is question placement in
`packages/derivation/presentation_projection.py:_closure_question_reasons`:
the new line-6b explanation would need field/branch applicability instead of
an unconditional fact-global join. `input-question.v1` has no applicability
property and forbids additional properties
(`packages/schemas/derivation/input-question.v1.schema.json:4`); a declarative
solution may also need a schema successor. P0 stops here. No such design or
implementation was attempted after this finding, and no projection/page work
was taken from the other milestone.

## Recommendation and decisions for the foreman

Do not launch the ten-question build unchanged under the present target.
Disposition the placement finding first.

- Confirm the reproduced scope: ten absent question citizens, not empty
  expression-block metadata. A v17 worksheet successor is not justified by
  this evidence.
- Decide whether asking an already-required line-6d living-arrangement
  question on a computing no-benefits return is acceptable. If it is, revise
  the no-new-question target explicitly before adopting this content design.
- If it is not, charter field/branch-aware question placement and coordinate
  the projection overlap with blocked-sale-pages. A schema/engine change is
  not authorized by this builder charter.
- The nine other missing scope questions are independently useful, but
  publishing only them would leave the separate-filing line-6b case unresolved;
  do not call that partial repair complete.
- Keep actual lump-sum-election sources outside the claimed reachable class;
  this milestone does not change source admission or its false-only witness.
- Preserve the recorded replay as parity evidence, including its 84 matching
  errors and zero fully-computing-list denominator. Track 0 needs explicit
  current computing coverage, rather than reading the raw replay as proof
  of the no-new-question target.
- Reconcile the package version with whatever core is published when a build
  is finally chartered; scratch v92 is evidence notation only.
