## Protected personal-loss case

`exception1_personal_loss_8949` means an actual personal-item loss is reported
on Form 8949, with no supported sale record. Its eight answers are already
recorded. Replacing each one separately with yes and no produces sixteen
live runs. **None unblocks line 16 or moves its four-name block.**
In the cumulative counterfactual, changing only-box-2a to yes still leaves
the same block. Also changing no-capital-losses to yes changes the conclusion
to no and moves line 16 to its ordinary dependency block; it still does not
compute because the recorded Form 8949 work remains. The remaining two
Exception 1 answers are already yes. These counterfactuals are routing
evidence, not truthful resolutions of the stipulated case.

`law.json` checks every exact sentence and records each individual result.
It includes source identities, SHA-256 hashes and PDF-page locators for the
local 2025 IRS instructions. Their relevant headings are Form 1040 line 7a,
Exception 1; Schedule D's personal-use assets and nondeductible losses; and
Form 8949's personal items and adjustment-code table. A personal loss can
require reporting while being nondeductible; its code-L adjustment prevents
treating it as the deductible securities loss the earlier harness's
“resolved-personal-loss” helper substitutes. This P0 never uses that helper
as a truthful resolution.

This is a conservative product judgment for foreman disposition, not a claim

## Design comparison

`prototype.py` loads the earlier published-content successor builder by
path under a unique module name, starts from published v94, and generates
scratch core v95 / registry v93 / release v93 outside Git. It replaces only
`rule.form1040-line16` v8 with v9 on the already published rule-artifact v17.
The original guard and four-name block remain. Inside that block, a required
Schedule D and a no-Form-8949 answer of yes select eight names; no selects
four. The schema, value, requires, pins and fallback block declarations are
unchanged. No answer or refusal code is introduced. The distinguishing answer
is already needed by the preferential-base path; the new guard consults it
so it can choose truthful names.

| Alternative | Result / cost |
| --- | --- |
| Broad successor, conclusion yes alone | Smallest syntax; `boundary.json` proves it changes the protected case too. Reject the implication that Exception 1 can truthfully excuse the reported personal item. |
| Narrow successor, also consult existing Form 8949 boundary | Preferred prototype. Fixes the target and all four dependants; all ten pinned cases stay identical. Adds a guard read of an existing path answer. |
| New dependant rules | Unnecessary: the actual projection already follows line 16. |
| Projection/page repair | Wider behavior and overlaps blocked-sale-pages; not prototyped or needed. |

`boundary.py` additionally withdraws the distinguishing answer on single,
joint and separate required returns. The new guard becomes unresolved and
uses line 16's existing dependency fallback: the row names taxable income,
preferential base and worksheet lines 24/25; the page routes to the existing
unanswered boundary. V94 instead retained its four explicit sale names.
Both cores remain blocked `DEPENDENCY_ABSENT`, with unchanged values.
This is a measured naming change within required/no-sale states, not a new
answer requirement. The foreman must explicitly decide whether this open
boundary behavior belongs in the contract before Track 0.
