## Identity, scope, and currentness trace

The question about basis not reported is
`tax.us.2025.f1099b.noncovered-sold.source-closure`, declared by
`packages/content/tax/2025/input-question.f1099b-noncovered-sold.json:2-9` and
mapped to the sentence by
`packages/content/tax/2025/closure-mapping.f1099b-noncovered.json:2-14`. The
input-question object ID is
`tax.us.2025.input-question.f1099b-noncovered-sold`; its `fact_type` is the
answer key above. The mapping applies that answer to
the noncovered short- and long-term sale, proceeds, basis, and adjustment
families. The fixture also carries a separate answer key,
`tax.us.2025.f8949.no1099b-sold.source-closure`, for sales without a Form
1099-B. It has different wording and is answered `no` in both v89 carries.
The stale case also records a separate `tax.us.2025.schedule-d-boundary.noncovered-in-class`
scope fact as `yes`. These keys describe distinct inputs; the answered
no-1099-B input does not answer the basis-not-reported question.
The separate no-1099-B prompt is declared in
`packages/content/tax/2025/input-question.f8949-no1099b-sold.json:2-9`.
The observation manifest writes the no-1099-B `question_key` and the
basis-not-reported `source_question` separately
(`tools/sale_page_observation.py:1426-1440`).

The stale fixture is built as `_after_sale("no", None, "late")` in
`docs/phases/engine-breadth/milestones/noncovered-sales-evidence/p0b.py:481-488,511`.
It opens with the `no` closure answer, then `_lt_sale` adds a long-term sale and
its proceeds and basis members (`p0b.py:419-429`), without recording a later
answer. The added
long-term member advances that family's horizon from
`demo.ns.p0b.noncovered-lt.h0` to `demo.ns.late.noncovered-lt.h1`. The old
finding `demo.ns.p0b.no` remains in the log under
`tax.us.2025.f1099b.noncovered-sold.source-closure|tax-year=2025`, but it does
not establish completeness for the changed long-term family. The run manifest
labels the input `stale-no`; that label is harness metadata, not a status saved
on the presentation-model reason. The input chronology comes from the source
fixture; the coordinator output independently shows the current transaction's
amount check blocked.

Core v89 Schedule D line 9 requires the long-term proceeds, basis, adjustment,
and per-sale amounts-check results
(`packages/content/tax/2025/rule.schedule-d-line9.v3.json:12-25`). In the stale
model, the amounts-check child is blocked with
`DEPENDENCY_INVALID`, missing the current transaction fact
`tax.us.2025.f1099b.noncovered-lt-txn|broker=demo.ns.late.broker,statement=demo.ns.late.statement,transaction=demo.ns.late.transaction,tax-year=2025`.
Its rule reads each sale's `amounts-agree` subject result
(`packages/content/tax/2025/rule.f1099b.noncovered-lt-txn.amounts-check.json:33-56`),
but that missing transaction fact is not itself a declared input question.

The stale line loses its known closure question in
`packages/derivation/presentation_projection.py`, not in the renderer. The
projection maps closure families and input fact types to declared question
sentences (`presentation_projection.py:508-528`), then walks every missing
dependency (`presentation_projection.py:565-593`). In the stale run, the walk
reaches the amounts-check branch and cannot map its missing transaction fact to
a question or declared meaning. `reach_mixed` therefore fails the whole walk;
the later guard returns an empty reason list even though the other branches
identify the noncovered closure question (`presentation_projection.py:624-641`).
The renderer then uses the field's generic explanation because
`resolved.reasons` is empty (`packages/presentation/pages/citation-walk.v1.html:1034-1055`),
using the existing Schedule D line 9 blocked explanation in
`packages/content/tax/2025/schedule-d.line-9.form-field.json:32-38`. The unanswered case
has no such extra invalid amounts-check branch, so its question survives as a
line-local reason.

The harness `cases.json` preserves `question_key`, `source_question`, the
answer state, and the recorded source closure for diagnosis. The saved
presentation model does not preserve that relationship on a blocked reason:
`_closure_question_reasons` turns the fact/family mappings into a set of
sentences and emits only `{"sentence": ...}`
(`presentation_projection.py:624-633`). The page renderer also reads only
`reason.sentence`. Question ID, fact type, family scope, currentness, and
source finding are absent from the saved reason. Equal sentences are deduped
within a row, while one shared answer key is repeated on many rows; this
produced the 39 and six visible occurrences above.

On the line-9 section itself, the blocked `resolved.act` is null; in the stale
case `resolved.reasons` is also absent. Its `dispositionNodes` preserve the
missing dependency tree and exact transaction identity, not a link back to the
source question. The old answer finding is still pinned by some neighboring
line derivations, but it is not connected to the line-9 reason.

The two sale answer keys in these captures have different wording, so this P0
does not claim to have observed two independent sale questions with identical
text. The saved representation still cannot distinguish such a pair: identity
is discarded before the saved model, and sentence equality is the deduplication
key.

## Smallest supported design

Keep a blocked reason as a typed reference to its source question rather than
only its sentence. It needs the stable question ID and fact type, the family
scope whose closure is needed, whether that answer is current for that scope,
and the declared sentence. Deduplicate prompts by answer identity and scope,
not by wording, and let each affected row reference that prompt. Preserve
separate non-question causes alongside known answer prompts so one unmapped
dependency does not erase all known questions.

For this stale case, the available question is the existing
basis-not-reported closure question, scoped to the long-term family after its
new member. The additional amount-check blocker needs its own safe explanation
if it is to be shown separately. P0 found no declared input question for that
missing transaction result, so I have not invented one. The existing generic
line explanation can continue to describe that the sale must pass its checks.
The trace supports a bounded saved-page/projection follow-up; it does not yet
establish whether structured question references can be added compatibly to
the persisted model. If that requires a schema or new question content, stop
for owner direction as the milestone plan requires.
