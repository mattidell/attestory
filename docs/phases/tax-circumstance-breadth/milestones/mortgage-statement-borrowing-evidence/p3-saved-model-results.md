# P3 saved-model feasibility — bounded result

This is presentation-feasibility evidence only. The P2 synthetic content and its six case inputs were reused; no tax rule, evaluator, resolver, runner, coordinator or production package was edited. The probe code is [p3-saved-model-probe.py](p3-saved-model-probe.py). Generated overlay modules, coordinator reports, presentation models, record snapshots and HTML serialization outputs are ignored under `temp/mortgage-statement-borrowing/`.

## Method and boundary

The probe generated an overlay module and loaded it with `importlib` in a dedicated process. It replaced only `live.build_presentation_model`, the internal mortgage explanation builder and its strict presentation-model validation functions (including the saved-session validation reference). The real `live_coordinate_run`, package resolver, evaluator/dispatcher, tax content, record writer, coordinator dispositions and saved-model render/serialization path remained active. The process exited after each probe; no production code was patched.

The overlay retains the P2 derived reason finding and its pinned answer chain for each report, obtains the exact bridge producers and their raw input fact-type references from the selected rule pins, and records current shared account assertions by their actual source findings. It uses each bridge rule's exact `joined` reference only to resolve raw answer labels through the existing lineage helper; it does not change rule evaluation or synthesize answer findings. Exact rule ID/version, pins, source identities, model run ID and workspace revision are retained. P2's manual borrowing key and answers remain synthetic supplied assertions, not recorder evidence.

The first successful positive run used overlay SHA-256 `ec85ba7c3cebbf20145f96f472ab12ac7bf668693f02fe0f25ae0b33f6c0360f`; the five remaining P2 cases and singleton control used `ef5944a298c76e8e07e14d85da77b0174b418c06e7efb1a4517b78651f4a63a`; the corrected closed-empty control used `c3b9f89329212df86faecb3b2e446ea4fd39048534c512ac3cf69d575d9a7f7f`. The exact overlay bytes are retained beside each run in `temp/`.

## What this establishes—and does not

The P2 coordinator can produce a durable two-report model through a presentation-only adapter; the model shape can preserve each report's raw amount and reason lineage, shared source support, actual per-report results, the line8a disposition, exact rule pins and saved-run identity. The same real reload/HTML serialization path accepted the model, and incumbent singleton plus genuine closed-empty v49/v47 paths were compatible with the overlay. This is not evidence that the group is visibly rendered: `_render_page` reloaded, validated and serialized the model into HTML, but the current product page renderer's singleton reader was not changed or browser-executed for the v2 group. HTML byte counts are not visual-delivery evidence.

Not built or demonstrated: a mortgage account/entity and relationship recorder; authoritative borrower identity; production route selection for connected versus no-activity activity; current affirmed/denied/cannot-tell/withdrawn carriers and their correction/withdrawal/removal/re-recording semantics; late-report reclosure; connected withdrawal without singleton fallback; production saved group reader/UI; production content/schema adoption; a clear-account exit. The saved-run helper was exercised on the five remaining synthetic cases and controls, not on the retained positive run. The initial malformed harness attempts and one registry-mismatched empty-control fixture were setup failures, not tax-case outcomes; they were corrected before the bounded cases were recorded.

The actual consumer boundary remains indirect: `attachment.schedule-a.json` owns the F1098 Schedule A row-set/tie-out for line8a; there is no direct line8a form field. The form-facing field is `form1040.line-12e.form-field.json` bound to `tax.us.2025.deductions.line-12e`, with line8a consumed downstream through the Schedule A/excess-over-standard and Form 1040 line12e rules. The closed-empty model exposes the configured `15000` line12e value through the existing no-statement path while its Schedule A attachment is inapplicable. Thus this probe establishes a valid internal saved model and HTML serialization, not final line12e form display.

## Connected consumer source trace and next discriminating case (not run)

The saved positive coordinator disposition is decisive: line12e blocks `DEPENDENCY_ABSENT` for `tax.us.2025.schedule-a.line8a` even though that publisher later publishes. In the adopted `rule.form1040-line12e` v1, `requires` contains only `demo.form1040.standard_deduction` and `tax.us.2025.f1098-scope.no-mortgage-statement`; line8a appears only as a value-expression reference in the nonempty, not-Path-A branch. `packages/derivation/runner.py`'s ordinary saturation loop calls `attempt` as soon as declared requirements exist. `attempt` evaluates the rule value, records an `EvalBlocked` as a disposition and marks the rule resolved. Since line8a was not a declared prerequisite, line12e is not deferred and its missing branch reference becomes a terminal block; later line8a publication does not retry it. This is existing rule/content behavior, not an engine or schema limitation.

The smallest candidate ordering repair is a successor line12e rule content change that adds the already-adopted `tax.us.2025.schedule-a.total` to `requires` and its declared input pins, leaving its guard and value expression intact. The adopted nonempty `rule.schedule-a-total` requires line8a, while `rule.schedule-a-total-closed-empty` requires nothing and publishes zero only when the F1098 family is closed-empty. Therefore the added dependency should order nonempty line12e after line8a through the total, and keep the existing closed-empty route eligible after total zero. It should also preserve the existing one-report line8a path where that path publishes; an unresolved line8a should continue to block rather than permit a raw-itemized bypass. This is a source-derived proposal only: no package overlay, validator check or coordinator execution for this change has been made. No extra route selector or engine/schema change is indicated by this trace.
