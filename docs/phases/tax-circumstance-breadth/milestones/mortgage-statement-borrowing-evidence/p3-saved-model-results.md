# P3 saved-model feasibility — bounded result

This is bounded prototype evidence, not production implementation. The first stage tested a presentation-only overlay; later stages also executed two explicit, ephemeral content successors (line12e ordering and Schedule A attachment completeness). No committed production code or content changed. The P2 synthetic content and its six case inputs were reused. The probe code is [p3-saved-model-probe.py](p3-saved-model-probe.py); generated overlays, successor packages, coordinator reports, presentation models, record snapshots and HTML serialization outputs are ignored under `temp/mortgage-statement-borrowing/`.

## Method and boundary

The probe generated an overlay module and loaded it with `importlib` in a dedicated process. It replaced only `live.build_presentation_model`, the internal mortgage explanation builder and its strict presentation-model validation functions (including the saved-session validation reference). The real `live_coordinate_run`, package resolver, evaluator/dispatcher, tax content, record writer, coordinator dispositions and saved-model render/serialization path remained active. The process exited after each probe; no production code was patched.

The presentation overlay retains the P2 derived reason finding and its pinned answer chain for each report, obtains the exact bridge producers and their raw input fact-type references from the selected rule pins, and records current shared account assertions by their actual source findings. It uses each bridge rule's exact `joined` reference only to resolve raw answer labels through the existing lineage helper; it does not change rule evaluation or synthesize answer findings. Exact rule ID/version, pins, source identities, model run ID and workspace revision are retained. P2's manual borrowing key and answers remain synthetic supplied assertions, not recorder evidence. Later disposable content successors changed only line12e declared ordering and, separately, the attachment's legacy completeness-presence check; neither was adopted into production.

The first successful positive run used overlay SHA-256 `ec85ba7c3cebbf20145f96f472ab12ac7bf668693f02fe0f25ae0b33f6c0360f`; the five remaining P2 cases and singleton control used `ef5944a298c76e8e07e14d85da77b0174b418c06e7efb1a4517b78651f4a63a`; the corrected closed-empty control used `c3b9f89329212df86faecb3b2e446ea4fd39048534c512ac3cf69d575d9a7f7f`. The exact overlay bytes are retained beside each run in `temp/`.

## What this establishes—and does not

The P2 coordinator can produce a durable two-report model through a presentation-only adapter; the model shape can preserve each report's raw amount and reason lineage, shared source support, actual per-report results, the line8a disposition, exact rule pins and saved-run identity. The same real reload/HTML serialization path accepted the model, and incumbent singleton plus genuine closed-empty v49/v47 paths were compatible with the overlay. This is not evidence that the group is visibly rendered: `_render_page` reloaded, validated and serialized the model into HTML, but the current product page renderer's singleton reader was not changed or browser-executed for the v2 group. HTML byte counts are not visual-delivery evidence.

Not built or demonstrated: a mortgage account/entity and relationship recorder; authoritative borrower identity; production route selection for connected versus no-activity activity; current affirmed/denied/cannot-tell/withdrawn carriers and their correction/withdrawal/removal/re-recording semantics; late-report reclosure; connected withdrawal without singleton fallback; production saved group reader/UI; production content/schema adoption; a clear-account exit. The saved-run helper was exercised on the five remaining synthetic cases and controls, not on the retained positive run. The initial malformed harness attempts and one registry-mismatched empty-control fixture were setup failures, not tax-case outcomes; they were corrected before the bounded cases were recorded.

The actual consumer boundary remains indirect: `attachment.schedule-a.json` owns the F1098 Schedule A row-set/tie-out for line8a; there is no direct line8a form field. The form-facing field is `form1040.line-12e.form-field.json` bound to `tax.us.2025.deductions.line-12e`, with line8a consumed downstream through the Schedule A/excess-over-standard and Form 1040 line12e rules. The closed-empty model exposes the configured `15000` line12e value through the existing no-statement path while its Schedule A attachment is inapplicable. Thus this probe establishes a valid internal saved model and HTML serialization, not final line12e form display.

## Connected-consumer ordering follow-up (bounded execution)

The saved positive coordinator disposition is decisive: line12e blocks `DEPENDENCY_ABSENT` for `tax.us.2025.schedule-a.line8a` even though that publisher later publishes. In the adopted `rule.form1040-line12e` v1, `requires` contains only `demo.form1040.standard_deduction` and `tax.us.2025.f1098-scope.no-mortgage-statement`; line8a appears only as a value-expression reference in the nonempty, not-Path-A branch. `packages/derivation/runner.py`'s ordinary saturation loop calls `attempt` as soon as declared requirements exist. `attempt` evaluates the rule value, records an `EvalBlocked` as a disposition and marks the rule resolved. Since line8a was not a declared prerequisite, line12e is not deferred and its missing branch reference becomes a terminal block; later line8a publication does not retry it. This is existing rule/content behavior, not an engine or schema limitation.

The content-only ordering candidate is successor `tax.us.2025.rule.form1040-line12e@v2`: it adds `tax.us.2025.schedule-a.total` to `requires`, an input pin (`version: v1`, `origin: assertion`, matching the existing `rule.schedule-a-excess-over-standard.json` convention), and adds it to `blocked.missing`. The guard and value expression are unchanged. The temporary v52 package (based on retained P2 v51 graph) passed `resolve_production_package`; its package checksum is `c154bd50ad5569b17317f172dc9c0b47f9bcf8d304d6d7c3848c1e96467857b1`. ## Attachment completeness successor (bounded prototype)

Current `attachment.schedule-a.json` is `attachment-rule.v4`. Its `completeness.required_answers` has one presence-only entry for `tax.us.2025.f1098.liable-and-paid` plus seven value-checked `...schedule-a-boundary.*-declared == "yes"` entries. The `attachment-rule.v4` schema permits retaining those seven entries alone: at least one answer is required, and all seven value checks remain. The requirement/threshold, itemization row set, `single_family` authority, line8a subtotal, and line8a tie-out need not change. Temporary connected line8a v3 requires borrowing-readiness; readiness requires both report-local reasons and shared support, and each reason's pinned chain includes that report's own `paid-the-interest` answer. Thus the actual connected line8a amount already carries per-report paid-interest support without an independently asserted legacy `liable-and-paid` fact.

The active P1/P3 contract specifies nine current report-local answers, including `paid-the-interest`, but not an additional independent legacy `liable-and-paid` answer. The currently adopted singleton line8a v2 also requires report-local `paid-the-interest`; `liable-and-paid` remains an attachment completeness requirement (and a v1 line8a input), not one of the chosen nine-answer confirmations. The charter authorized an ephemeral successor-content prototype, not production acceptance. It removes only the legacy presence-only `tax.us.2025.f1098.liable-and-paid` completeness answer, retaining all seven boundary `value == "yes"` checks, the requirement/threshold, `single_family` authority, collector, row-set, line8a subtotal and tie-out. The selected ordinary-answer line8a rule v3 requires readiness; readiness requires both per-report reason chains and shared support, and each reason's pinned chain carries that report's `paid-the-interest` answer. Thus the connected line8a output supplies relevant payment support for this path without fabricating the independent legacy boolean. This is an explicit content delta for the prototype only; older packages are not thereby relaxed.

No published schema successor, engine change, production content edit, package/test change or broad test run was needed for this feasibility probe. The content delta and successful attachment disposition are prototype evidence only.
